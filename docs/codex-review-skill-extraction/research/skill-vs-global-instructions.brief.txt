# Research brief — moving a mandatory agent contract from a global instruction file into an elected skill

## Context (verified facts, not assumptions)

A solo maintainer runs Codex CLI (`codex exec`, codex-cli 0.145.0) in two distinct roles from
a Claude Code pipeline: **research** (GPT-5.5) and **adversarial code review** (GPT-5.6 Sol,
xhigh). Both are invoked non-interactively as:

    codex exec --skip-git-repo-check --ephemeral -s read-only -C <scratch-dir> -m <model> \
      -c model_reasoning_effort="xhigh" "<short prompt>" < bundle.txt

Today the *entire* adversarial-review contract lives in `~/.codex/AGENTS.md` — Codex's global,
always-loaded instruction file. That contract is large and highly specific: a reviewer identity
("you are the maintainer's dedicated adversarial researcher and reviewer"), six review axes,
scale-fit guards, a `Sites:` blast-radius finding format, a bounded `Sketch:` rule, a
severity-differentiated output budget, per-finding `Evidence:`/`Verification:` lines, and a
mandatory `GPT verdict:` closing line.

The problem the maintainer hit: `~/.codex/AGENTS.md` applies to **every** Codex invocation in
**every** project — including unrelated work like writing reports, drafting, or general
assistance. A review-shaped identity and output contract is contamination for all of those.

The proposed change: extract the review contract into a Codex **skill**
(`~/.codex/skills/<name>/SKILL.md`, same frontmatter shape as Claude skills: `name` +
`description`), leaving `AGENTS.md` thin and role-neutral, and have the calling prompt tell
Codex to use that skill when a review is requested.

**Already verified locally by direct experiment (do not re-research these):**
- A user skill placed at `~/.codex/skills/<name>/SKILL.md` IS discovered and loaded under
  `codex exec --ephemeral -s read-only -C <scratch>` — cwd outside any repo. A probe skill
  returned its sentinel string verbatim when the prompt named it.
- `~/.codex/AGENTS.md` is likewise loaded under those same flags.

## The central question

Global instruction files are **unconditional**: the runtime injects them. Skills are
**elected**: the model decides whether a skill applies and reads it. Moving a *mandatory*
contract from the first category to the second trades ambient correctness for scoping.

Research this trade with both-sides evidence:

1. **Reliability of model-elected skill invocation.** What is known — from OpenAI/Anthropic
   primary documentation, agent-framework literature, and any empirical study — about how
   reliably an agent loads a skill when instructed to by name in the prompt, versus when it
   must infer applicability from the skill's `description`? Are there measured failure rates,
   known failure modes (skill ignored, partially read, summarized rather than followed), or
   documented guidance about not putting must-follow constraints in electable units?

2. **Prior art on scoping agent instructions.** How do current agent systems draw the line
   between always-on instruction files (AGENTS.md, CLAUDE.md, system prompts) and on-demand
   units (skills, tools, subagent definitions)? Find explicit vendor guidance on what belongs
   in each. Specifically: is there documented advice about role/persona statements in a global
   file when the same binary serves multiple unrelated roles?

3. **The contamination claim, examined honestly.** Is there evidence that a strong,
   role-specific persona and output format in an always-loaded instruction file measurably
   degrades unrelated tasks (e.g. a reviewer persona making a model terser, more critical, or
   more likely to emit findings-shaped output when asked to write a report)? Or is the effect
   small enough that scoping is mostly hygiene? Look for prompt-contamination / persona-bleed /
   instruction-interference studies.

4. **Fail-loud designs for elected contracts.** If a mandatory contract lives in a skill, what
   are documented patterns for detecting non-loading at runtime? The maintainer's current
   approach is to have the prompt order a hard stop with a stated first line if the contract is
   absent. Is self-report a credible detector, or is there prior art showing models
   confabulate having loaded instructions they did not? Look for evidence about models
   falsely claiming to have read a file or followed a rule.

5. **Middle options.** Is a hybrid defensible — a thin always-on line in `AGENTS.md`
   ("when asked to review, load the codex-review skill and follow it exactly") plus the full
   contract in the skill? What does that buy and cost versus a pure split? Are there other
   mechanisms in Codex CLI specifically (per-project `AGENTS.md`, `--config` overrides,
   profiles, or prompt-only delivery) that serve this better?

6. **Codex CLI skill specifics.** Any primary documentation on: how Codex discovers user skills
   vs `.system` skills; whether a skill can be forced rather than elected; whether
   `codex exec` exposes a flag to preload or require a skill; how skill `description` text
   affects election; and whether skills are read fully or summarized.

## Output requirements

Cite current primary sources with URLs and dates. Mark clearly what you could NOT verify —
especially anything about Codex CLI skill-election mechanics, for which public documentation
may be thin. Where evidence is absent, say so plainly rather than generalizing from unrelated
work. Give the strongest argument AGAINST making this change (i.e. for leaving the contract in
the always-loaded file), not only support for it.
