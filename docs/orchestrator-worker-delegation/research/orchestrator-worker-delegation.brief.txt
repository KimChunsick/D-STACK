# Research brief — should ALL implementation work be delegated to worker subagents?

## Context
A single-maintainer AI-agent pipeline ("full-cycle") runs in Claude Code. Today:
- The main loop (orchestrator) does: intent, research, interview, decomposition, doc writing,
  adversarial code review (a separate model, GPT-5.6 Sol, via a CLI), and end-to-end verification.
- Implementation is delegated to worker subagents in git worktrees ONLY when a deterministic
  checker returns a PARALLEL verdict (candidate tasks are dependency-incomparable and their
  declared file sets are disjoint). Otherwise the orchestrator implements directly, serially.
- Frontend code is always delegated regardless of parallelism.

## The proposed change
1. Change the delegation gate from "PARALLEL verdict" to "the task has a complete declaration"
   (declared dependencies + declared file ownership), so serial tasks are delegated too.
2. Add an attribution rule for adversarial-review findings: a finding whose fix lies entirely
   inside ONE task's declared files goes back to that same worker with its context still warm
   (Claude Code's SendMessage continues a previously spawned agent); a finding that crosses
   declarations or touches orchestrator-owned paths (docs/, the pipeline's own skill files) is
   fixed by the orchestrator.

## Motivation, with measured numbers
A recently completed Goal in this pipeline burned 205,400 tokens of conversation messages against
37,000 tokens of fixed overhead (system prompt, tools, memory files, skills) in one session.
The 205k is implementation transcript: tool calls, file contents, iteration. Moving that into
worker contexts is the point. Auto-compact window is 563k tokens; compaction fires near 530k.

## Counter-evidence already known to the requester (verify, extend, or refute)
In that same Goal, the adversarial review loop ran 19 rounds across two review units. Many fixes
were "the sibling case of the fix you just made" — a repair to one function revealing the same
class in an adjacent one, and a repair that over-corrected a previous round's repair. Those
depended on holding several rounds of reasoning in ONE context. A worker confined to one task's
declared files could not have made some of them: one finding spanned three files across two
different declarations.

## What to research, with CURRENT primary sources where possible

1. Orchestrator/worker (supervisor/agent, manager/worker) patterns for LLM coding agents.
   What does published evidence say about WHEN decomposition into fresh-context workers improves
   outcomes, and when it degrades them? Look for measured results, not vendor claims.

2. The cold-start cost of a fresh-context worker. What is known about how much of a delegating
   agent's accumulated understanding must be re-serialized into a brief, and what is lost? Any
   published failure taxonomy for multi-agent handoff (dropped constraints, repeated discovery,
   contradictory assumptions)?

3. Anthropic's own published guidance on Claude Code subagents and multi-agent systems:
   documented context-isolation semantics, agent lifetime, whether a spawned subagent can be
   resumed later with context intact, and any stated limits. Also whether subagent context
   survives the parent session being compacted or cleared.

4. Task shape as the delegation criterion. Is there evidence distinguishing tasks that delegate
   well (a written spec, bounded file set) from tasks that do not (exploratory debugging,
   iterative review-response where step N depends on what step N-1 found)?

5. Git worktree necessity. If delegated work is SERIAL, is per-task worktree isolation still
   justified? What are the costs (dependency install, shared runtime resources like ports and
   test databases) versus letting a serial worker edit the main checkout? Note that this
   pipeline's containment check requires a clean tree and a committed base..HEAD range, which a
   worker editing the main checkout would not satisfy.

6. The "expensive model as a router" objection. The requester's own standing rules say not to use
   a model for routing or deterministic transforms. If an orchestrator only decomposes and routes,
   is that a known anti-pattern, and what do practitioners recommend instead?

7. Evidence AGAINST the change: cases where a single long-context agent outperformed a decomposed
   multi-agent setup on software tasks; cost analyses showing delegation increases total tokens
   even when it reduces one context; and any evidence that review-fix loops specifically resist
   decomposition.

## Deployment envelope (right-size the findings, do not waive concrete defects)
One maintainer, a few interactive terminal tabs, local disk, no CI fleet, no team. The pipeline's
artifacts are instruction documents and small shell scripts, not a distributed system.
