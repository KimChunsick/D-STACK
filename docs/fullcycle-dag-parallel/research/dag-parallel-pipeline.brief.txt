Research brief — DAG-parallel task execution for an LLM-agent delivery pipeline, plus structured pipeline-definition format

Context:
The maintainer runs a mandatory personal delivery pipeline ("full-cycle") inside Claude Code for every implementation task. Today it is strictly sequential: intent capture -> tri-axis risk evaluation -> delegated web research -> user interview -> decomposition into one Goal / milestones / PR-sized tasks -> per-task TDD (Red-Green-Refactor) -> per-task adversarial review by a second model (Codex CLI, "codex exec", one review round per numbered markdown file, consensus loop) -> per-task E2E evidence capture -> per-milestone E2E -> final Goal E2E. A Stop hook (bash) blocks the session from ending while any registered doc has unchecked gate checkboxes. Reviews are scoped by a fail-closed per-task file allowlist; a review round is voided if files in its bundle change mid-round. The pipeline is defined as a prose markdown skill document (~250 lines) that the orchestrating LLM re-reads and interprets each session.

Planned change:
1) Within each milestone, declare inter-task dependencies at decomposition time and schedule tasks as a DAG: independent tasks run their implementation (delegated to worker subagents), TDD, and adversarial review in parallel; a dependent task waits for its predecessors; when a predecessor finishes, newly unblocked tasks fan out in parallel. Parallel implementation would use git worktree isolation per task (each worker gets its own worktree/branch; merges happen in dependency order). Each task's adversarial review stays scoped to exactly that task's files/diff.
2) Convert the prose skill document into a structured, machine-parseable representation (e.g. YAML/JSON phase+gate schema with short prose annotations) so the orchestrating LLM interprets it more deterministically and cheaply.

Research questions (gather both sides with current primary sources):
A. Parallel multi-agent code implementation: What is the current prior art and evidence (2024-2026) for running multiple LLM coding agents concurrently on one repository? Git-worktree-per-agent isolation patterns (e.g. Claude Code worktrees, Cursor/other agent farms, open-source orchestrators): benefits measured, and documented failure modes — merge conflicts, semantic conflicts that merge cleanly but break integration, test interference, shared-resource contention (ports, databases, lockfiles), context divergence between workers.
B. DAG/dependency-based task scheduling for agent pipelines: prior art for declaring task dependency graphs in agent workflows (CI systems, build systems, agent frameworks). Evidence on whether LLM-planned task decompositions produce reliable dependency edges, and known failure modes (false independence: tasks declared independent that actually touch the same files or contracts; hidden coupling through shared interfaces).
C. Review integrity under parallelism: for a reviewer that receives a per-task scoped diff, what are the risks of reviewing tasks in isolation while sibling tasks change the same codebase concurrently (review sees stale base, integration defects invisible to per-task review)? Mitigations: file-set disjointness checks, merge-order review, a final integration review pass.
D. Structured vs prose workflow definitions for LLM consumption: evidence for/against expressing an agent's operating procedure as a schema (YAML/JSON state machine, checklists with typed gates) versus natural-language prose. Does structure measurably improve instruction-following and reduce token cost / interpretation drift? Counter-evidence: rigidity, loss of nuance, schema-maintenance burden, models ignoring or misparsing YAML.
E. Wall-clock economics: does parallel agent implementation actually reduce end-to-end delivery time in practice, or do coordination, merge resolution, and re-review overheads eat the gains at small task counts (2-6 tasks per milestone)? Any measured data.

Also collect evidence AGAINST the whole goal: arguments that a sequential pipeline is safer/simpler for a single-maintainer project, that parallelism at PR-sized task granularity is premature optimization, and that the real latency bottleneck (long adversarial-review rounds of 15-25 minutes) is better attacked by other means.
